# ProdKit Workflows v0.0.0

Initial organization workflow control plane.

This release establishes reusable CI and Security matrices, exact-SHA guarded GitHub Releases, immutable tags, SPDX SBOM generation, provenance attestations, draft-first checksum-verified publication, consumer bootstrap contracts, importable organization rulesets, and organization-wide workflow drift auditing.

The final v0.0.0 contract supports GitHub-hosted-only, trusted self-hosted-only, or strict dual-runner CI/Security execution through `PRODKIT_RUNNER_MODE`. GitHub-hosted Ubuntu remains the fail-safe default; `both` runs the complete reusable contract independently on both runner classes and requires both; manual dispatch may override policy; and fork-originated pull requests are always forced onto GitHub-hosted runners.

GitHub Actions has no native ordered hosted-to-self-hosted fallback. During hosted quota/capacity incidents, ProdKit redispatches the same exact SHA to self-hosted capacity rather than using `both`. Release accepts successful exact-SHA required-workflow evidence from either normal `push` execution or trusted `workflow_dispatch` failover, while PR-only evidence remains invalid. Release itself remains single-runner so publication transactions cannot race.

CI and Security adapter paths are runtime-contained beneath `.prodkit/workflows/`; full-history Gitleaks produces redacted evidence and supports repository-contained reviewed allowlists; release-manifest v1 is strictly shape-validated; and consumer release output is rejected if it is empty, nested, symlinked, or attempts to overwrite central proof/source/SBOM artifacts. Contract tests lock these guarantees to `docs/CONTRACTS.md`, bootstrap output, local validators, and reusable workflow behavior.

The workflow surface is intentionally layered rather than one-to-one: `.github/workflows/` contains 8 YAML files (4 operator-facing workflows plus 4 reusable implementations), the generated consumer adapter catalog contains 11 shell adapters, and this control-plane repository itself enables only 4 `.prodkit/workflows/` adapters. Disabled capabilities do not require local adapter files; enabling a capability makes its configured adapter mandatory and runtime-validated.
