# ProdKit Workflows v0.0.0

Initial organization workflow control plane.

This release establishes compact-default and expanded-compatible reusable CI/Security orchestration, exact-SHA guarded GitHub Releases, immutable tags, SPDX SBOM generation, provenance attestations, draft-first checksum-verified publication, guarded metadata-only repair for already-published Releases, consumer bootstrap contracts, importable organization rulesets, organization-wide workflow drift auditing, and hosted-first automatic runner failover.

The final v0.0.0 runner contract supports GitHub-hosted and trusted self-hosted execution through one condition-driven policy. `PRODKIT_RUNNER_MODE=auto` and an unset policy perform a minimal repository-code-free, non-poisoning `ubuntu-latest` availability probe before trusted workloads. The probe emits `available=true` only when a hosted runner actually starts; when that positive output is absent under auto policy, the unchanged reusable workflow is routed to `["self-hosted","Linux","X64"]`. `continue-on-error: true` prevents the infrastructure probe itself from poisoning an otherwise successful fallback workflow. Explicit `github-hosted` and `self-hosted` modes remain strict operator choices, manual dispatch can force `auto`, and fork-originated pull requests are always forced onto GitHub-hosted runners. Failover happens before product validation or release steps, so genuine test/security/publication failures never cause retry on another runner. Indefinitely queued hosted jobs and complete GitHub Actions control-plane outages remain outside in-workflow failover.

Generated consumers use compact CI and Security by default. Enabled Python/Node compatibility dimensions, PostgreSQL acceptance, custom checks, Gitleaks, dependency audits, container scanning, SBOM generation, and evidence handling execute as steps inside the stable `CI Required` or `Security Required` job rather than as a large set of independent GitHub jobs. Intermediate contract steps may continue after failure solely to collect complete evidence; the final verifier aggregates every enabled outcome and fails closed. Stable branch-protection identities therefore remain `ci / CI Required` and `security / Security Required` while Actions job/check fan-out is substantially reduced.

The original expanded `reusable-ci.yml` and `reusable-security.yml` remain part of the immutable API for already-pinned consumers and repositories that explicitly prefer independent parallel matrices. Compact CI supports the organization compatibility set Python 3.12/3.13/3.14 and Node 20/22/24 and rejects unsupported or duplicate version selections rather than silently weakening compatibility coverage.

CI and Security adapter paths are runtime-contained beneath `.prodkit/workflows/`; full-history Gitleaks produces redacted evidence and supports repository-contained reviewed allowlists; release-manifest v1 is strictly shape-validated; and consumer release output is rejected if it is empty, nested, symlinked, or attempts to overwrite central proof/source/SBOM artifacts. Contract tests lock these guarantees to `docs/CONTRACTS.md`, bootstrap output, local validators, generated caller routing, compact/expanded workflow behavior, and reusable workflow behavior.

Release publication and release-presentation repair have deliberately separate trust boundaries. Publication requires the requested source SHA to be current `main` with successful exact-SHA CI/Security evidence and owns tag/artifact creation. Metadata repair is valid only for an already-published immutable tag: it uses current `main` solely as the canonical title/notes source, proves the tag still resolves to the supplied historical source SHA, verifies the complete published checksum set, changes only GitHub Release `name` and `body`, and re-verifies that tag identity, publication flags, asset identity, and payload checksums are unchanged.

The generated consumer lifecycle contains five required callers: CI, Security, Trusted Release Proof, Release, and Release Metadata. Organization audit validates all five against the correct reusable workflow family at the required immutable SHA; CodeQL remains opt-in.

The workflow surface is intentionally layered rather than one-to-one: `.github/workflows/` contains 16 YAML files (4 operator-facing workflows plus 12 reusable implementations), the generated consumer adapter catalog contains 13 shell adapters, and this control-plane repository itself enables only 4 `.prodkit/workflows/` adapters. Disabled capabilities do not require local adapter files; enabling a capability makes its configured adapter mandatory and runtime-validated.
