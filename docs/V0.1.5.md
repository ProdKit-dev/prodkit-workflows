# ProdKit Workflows v0.1.5

v0.1.5 completes the normal release lifecycle so consumers no longer need to orchestrate proof, publication, verification, or merged release-branch cleanup by hand.

## Lifecycle

The canonical happy path is now:

`release PR merge -> exact-main CI/Security/(CodeQL) -> automatic Trusted Release Proof dispatch -> automatic proof-to-promotion bridge -> protected release-environment approval when configured -> Release -> Release Verification -> automatic canonical Branch Cleanup`

`workflow_dispatch` entry points remain available for recovery and re-verification, but they are not the normal operator path.

## Automatic verified cleanup

`reusable-release-verification.yml` now dispatches the existing canonical Branch Cleanup workflow only after immutable release verification succeeds. Release Verification still cannot delete refs directly: it receives `actions: write` and `pull-requests: read` only so it can prove and dispatch cleanup, while the existing `branch-cleanup.yml` / `reusable-branch-cleanup.yml` boundary remains the sole `contents: write` deletion authority.

Automatic cleanup is fail closed. The verifier requires exactly one eligible same-repository PR branch associated with the immutable release commit, already merged to `main`, with `merge_commit_sha` equal to the verified release SHA and a branch prefix in the configured release namespace (`release/` or `hotfix/` by default). The branch must still point to the exact merged PR head SHA. If `main` advanced after release, the verified release SHA must remain its merge base/ancestor; cleanup is then dispatched with the current default-branch SHA as the destructive guard. Missing/already-deleted branches are idempotent success; ambiguous or moved branches are not deleted automatically.

## Trust boundary

- Exact-main permanent gates remain source qualification.
- Trusted Release Proof remains dispatch-only and exact-source-bound, but v0.1.4+ callers dispatch it automatically after permanent gates complete.
- The protected `release` environment is the optional single human publication-approval boundary.
- Release Promotion, Release, Release Verification, and current release-branch cleanup are automatic after that boundary.
- Manual proof, release, verification, and Branch Cleanup remain explicit recovery tools.

## Consumer adoption

Consumers must pin all lifecycle reusables to the immutable v0.1.5 source SHA. Pins to v0.1.3, the pre-fix v0.1.4 candidate `1ed882908e5ff0fe6f61662ec924551137c60257`, or mixed lifecycle SHAs are considered drift and should be replaced as one coordinated workflow-only change.

Repository-specific CI/Security/CodeQL matrices, build adapters, release manifests, and runtime/package semantics remain owned by each consumer; v0.1.5 changes lifecycle orchestration only.
