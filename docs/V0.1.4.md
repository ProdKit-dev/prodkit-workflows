# ProdKit Workflows v0.1.4

`v0.1.4` removes the remaining manual release-candidate action without weakening the proof or publication trust boundaries.

## Outcome

After a release-intent merge reaches `main`, ordinary permanent `CI` and `Security` still certify the exact merge SHA. A new `Release Proof Dispatch` control-plane stage observes successful gate completion, confirms both exact-SHA gates are green, confirms the canonical manifest version is not already tagged, and then dispatches `Trusted Release Proof` automatically.

The proof workflow itself remains `workflow_dispatch` only and continues to certify `${{ github.sha }}`. This preserves the existing exact-proof evidence contract used by the guarded publisher while removing the need for an operator to click **Run workflow**.

## Release-intent boundary

The automatic dispatcher is deliberately narrow and non-mutating. It:

- requires the triggering SHA to still equal the current default-branch SHA;
- derives one canonical SemVer from `.prodkit/release.json` version sources;
- treats an already-published matching tag as no new release intent and fails closed if that canonical tag points elsewhere;
- waits logically, without polling, until every required exact-SHA push gate has completed successfully;
- fails closed if a required gate completed unsuccessfully;
- validates that the repository `Trusted Release Proof` caller remains `workflow_dispatch` only and source-bound to `${{ github.sha }}`;
- suppresses duplicate active or successful exact-source proof dispatches;
- rechecks current-main identity immediately before dispatch;
- runs GitHub-hosted with `actions: write` and `contents: read`, so it can start proof but cannot tag, publish, or edit repository content.

## Human approval boundary

Human authorization is not removed from publication policy. It belongs at the protected `release` environment immediately before the mutation/publish stage, rather than before evidence generation. CI, Security, proof, promotion and build/seal may proceed automatically; protected-environment approval remains the publication authorization boundary when the repository configures required reviewers for `release`.

## Completion topology

The normal path is now:

`main CI/Security → Release Proof Dispatch → Trusted Release Proof → Release Promotion → Release → Release Verification`

Both dispatcher stages are non-blocking and use `workflow_dispatch` to cross into the child workflow, avoiding single-runner deadlocks and GitHub chained-`workflow_run` depth suppression.

## Included correction

This release also includes the post-v0.1.3 regression fix that prevents `${{ github.sha }}` from being pre-expanded inside the verification-dispatch validator. The contract is now constructed at runtime and guarded by a dedicated regression test.

## Compatibility

Consumers pinned to earlier immutable releases keep their existing behavior. Consumers adopting v0.1.4 should repin the complete generated workflow family to the exact v0.1.4 release commit SHA and add `release-proof-dispatch.yml`; partial adoption is intentionally rejected by organization audit.
