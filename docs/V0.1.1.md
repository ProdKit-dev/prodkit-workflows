# ProdKit Workflows v0.1.1

`v0.1.1` is the first patch hardening release after the stable `v0.1.0` workflow-control-plane baseline. It adds centrally governed branch cleanup and fixes cancellation handling in compact CI/Security without changing the proof-once / publish-once release architecture established in `v0.1.0`.

## Outcome

The canonical lifecycle now includes a deliberate maintenance stage after merge/release closure:

`PR CI/Security → exact-main CI/Security → Trusted Release Proof → Release Promotion → resumable Release → Release Verification → explicit Branch Cleanup`.

Branch cleanup is intentionally separate from publication authorization. It never moves tags, changes releases, or participates in branch-protection required checks.

## Centrally governed Branch Cleanup

`reusable-branch-cleanup.yml` is now a normative reusable workload. The generated `branch-cleanup.yml` caller is `workflow_dispatch` only, defaults to dry-run, runs on GitHub-hosted `ubuntu-latest`, and grants write permission only to the cleanup job.

The cleanup contract accepts a non-empty JSON array of exact branch names. Wildcards and pattern expansion are not supported. Before any deletion the reusable workflow:

- requires the repository default branch to remain on the exact SHA reviewed at dispatch time;
- rejects the default branch itself;
- rejects malformed or duplicate branch names;
- treats already-absent refs as idempotent success;
- rejects protected branches;
- rejects branches that are the head of an open pull request;
- preflights the complete target set before any mutation.

For destructive execution, the workflow rechecks the default-branch identity before each deletion, rechecks open-PR and protection state, rereads the target ref, and requires its SHA to match the SHA validated during preflight. A moved, recreated, newly protected, or newly active PR branch is not deleted. Each successful deletion is read back and must resolve as absent.

Repository cleanup runs are serialized and emit structured evidence so operators can review the exact requested targets and outcomes.

## Consumer bootstrap and organization governance

`bootstrap_consumer.py` now installs `.github/workflows/branch-cleanup.yml` alongside CI, Security, release proof, promotion, publication, verification, and metadata callers.

Organization audit and contract tests enforce the same architecture:

- the canonical cleanup caller must be present;
- it must pin the same exact 40-character `prodkit-workflows` SHA as the other normative callers;
- `workflow_dispatch` must be its only trigger;
- the cleanup workload itself independently rejects non-`workflow_dispatch` invocation, so an alternate hidden caller cannot bypass the authorization boundary;
- cleanup remains GitHub-hosted and exact-default-SHA-bound.

Existing consumers pinned to older control-plane SHAs continue to work unchanged. Adoption of `v0.1.1` is explicit by repinning the full generated workflow set to the reviewed `v0.1.1` release commit SHA.

## Compact CI/Security cancellation hardening

Compact CI and Security aggregate verifiers now use `always() && !cancelled()` instead of unconditional `always()`.

This preserves fail-closed aggregation for genuine failures while avoiding false red outcomes when GitHub deliberately cancels a superseded run. A regression contract is executed by central CI to prevent the cancellation-poisoning behavior from returning.

## Documentation alignment

The README now exposes Branch Cleanup in the reusable workload table, bootstrap output, canonical lifecycle, and organization-audit guidance. It also documents the cancellation-aware aggregate behavior of compact CI/Security.

## Compatibility and versioning

The immutable `v0.1.0` tag and release remain unchanged. `v0.1.1` is a new patch-level checkpoint containing only additive maintenance hardening and the cancellation fix.

Production consumers should continue to pin a full 40-character `prodkit-workflows` commit SHA rather than a floating branch or tag. When adopting this release, bootstrap or manually update the complete workflow family to the exact `v0.1.1` release commit so CI, Security, cleanup, proof, promotion, release, verification, and metadata all share one reviewed control-plane revision.
