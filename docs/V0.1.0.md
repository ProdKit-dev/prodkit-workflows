# ProdKit Workflows v0.1.0

`v0.1.0` is the first stable operational release of the ProdKit organization workflow control plane. It turns the repository from an initial reusable-workflow bootstrap into the reviewed lifecycle that ProdKit consumers can pin as their release/CI/Security foundation.

## Outcome

The normative release path is now **proof once, build once, publish once**:

`PR CI/Security → exact-main CI/Security → Trusted Release Proof → Release Promotion → resumable Release → Release Verification`.

Permanent CI and Security results are treated as exact-SHA evidence rather than replayed inside release proof. Trusted Release Proof adds only release-specific acceptance and creates the repository-owned promotable payload exactly once. Release then imports that exact proof-produced payload, seals it with central evidence, and publishes it without rebuilding the same repository artifacts.

## CI and Security control plane

Generated consumers use compact CI and Security by default with stable required-check identities:

- `ci / CI Required`
- `security / Security Required`

Enabled Python, Node, PostgreSQL, custom, secret-scan, dependency-audit, container, SBOM, and evidence operations execute inside those aggregate jobs. Expanded reusable CI/Security workflows remain available for consumers already pinned to the historical parallel-matrix contract.

Runner selection stays direct and deterministic. Trusted callers provide a complete `runner_json` value, generated consumers default to `["self-hosted","Linux","X64"]`, `PRODKIT_RUNNER_JSON` can deliberately replace that target, and fork-originated CI/Security pull requests remain isolated on GitHub-hosted runners.

## Release proof and payload ownership

Trusted Release Proof is explicitly dispatched for the intended current `main` SHA. The reusable proof:

- proves the source is the exact current main commit;
- requires successful exact-SHA permanent `CI` and `Security` push evidence;
- runs only the consumer's release-specific proof adapter;
- executes the repository release-build contract once;
- validates the flat release payload;
- records artifact names, sizes, and SHA-256 digests in `release-payload.json`;
- uploads the proof evidence and promotable payload under the exact source SHA.

Generated proof adapters are intentionally prohibited from replaying permanent CI/Security matrices or calling `release-build.sh` themselves.

## Completed-proof promotion boundary

Promotion no longer occurs from a job inside the still-running proof workflow. `Release Promotion` is a separate `workflow_run` caller that starts only when the complete `Trusted Release Proof` workflow has reached `completed` with `success`.

That boundary removes the race where Release could query proof authorization while the proof run was still marked `in_progress`. Promotion carries the completed proof run's `head_sha`, derives the version from that exact source, dispatches Release idempotently, and exits without polling.

The adoption guide now reflects this automatic promotion path. Operators do not manually dispatch a second Release after a successful proof unless performing an explicit recovery after confirming automatic promotion created no active or completed exact-source Release run.

## Resumable immutable publication

The guarded publisher is split into independent stages:

1. **prepare** — validate version, current-main identity, manifest, exact-SHA CI/Security, and completed proof authorization;
2. **build/seal** — import the exact proof-produced repository payload, add central source/SBOM/metadata/checksum evidence, validate it, and upload a sealed workflow artifact;
3. **optional attestation** — attest the sealed payload only when explicitly enabled and supported;
4. **publish** — download the sealed payload, verify checksums, create or validate the immutable tag, resume/create a draft Release, reconcile only missing or mismatched draft assets, verify the complete draft, and publish.

The sealed workflow artifact is the retry boundary. A late attestation or publication failure can use GitHub **Re-run failed jobs** without rebuilding a successful payload. Existing correct draft assets are preserved rather than deleted and re-uploaded.

## Independent verification and metadata repair

Successful publication triggers read-only `Release Verification`, which independently proves immutable source, tag, release target, asset set, GitHub asset digests, and `SHA256SUMS` consistency.

`Release Metadata` remains a separate presentation-only trust boundary. It may repair canonical Release title/body only after proving tag and payload identity are unchanged; it cannot move tags, rebuild payloads, or silently mutate published assets.

## Artifact attestations

GitHub Artifact Attestations are an optional additional provenance layer rather than a universal prerequisite. Attestation defaults to disabled because repository/organization plan capability varies. When explicitly enabled it remains fail-closed. Exact-source proof, SBOM/checksum evidence, sealed-payload validation, publication read-back, and independent Release Verification remain required regardless.

## Consumer and organization governance

Bootstrap, templates, organization audit, lifecycle contracts, adoption guidance, and security documentation now enforce the same architecture:

- no floating central refs for consumers;
- no copied consumer proof API gate;
- no nested generated Release pipeline;
- no promotion job embedded in Trusted Release Proof;
- no release-build duplication between proof and Release;
- no permanent CI/Security replay inside proof;
- no polling child workflows while holding a scarce runner;
- exact immutable central workflow pins;
- compatibility wrappers remain compatibility-only rather than normative architecture.

## Compatibility

The release deliberately retains historical reusable entry points such as expanded CI/Security, `reusable-runner-policy.yml`, and `reusable-release-pipeline.yml` for already-pinned consumers. New generated integrations follow the compact direct-runner, completed-proof-promotion, proof-payload-reuse lifecycle described above.

`v0.1.0` is therefore the baseline ProdKit repositories should pin when adopting the current control-plane architecture.
